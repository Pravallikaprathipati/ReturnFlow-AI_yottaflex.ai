# Returns Workflow Simulator

A deterministic, synthetic returns-management workflow built with Python's standard library and SQLite. It creates linked customer, order, return, authorization, shipment, inspection, refund, inventory-disposition, and event-history records; applies documented policy; injects five explicitly labelled edge cases; and validates the resulting data.

No external dataset or real personal information is used. Challenge-specific wording is intentionally not reproduced in this repository.

## Requirements

- Python 3.11 or newer
- No third-party runtime dependencies

## Run it

From the repository root:

```powershell
python -m pip install -e .
python -m returns_workflow generate --scale starter --output data/starter
python -m returns_workflow validate --input data/starter
python -m returns_workflow verify-reproducibility --scale starter
python -m unittest discover -s tests -v
```

The starter scale generates 300 orders, 50 return requests, and 80 return lines. The assessment-scale dataset is generated by the same code and seed:

```powershell
python -m returns_workflow generate --scale full --seed 20261022 --output data/full
python -m returns_workflow validate --input data/full
python -m returns_workflow verify-reproducibility --scale full --seed 20261022
```

Use explicit counts for another scale:

```powershell
python -m returns_workflow generate --orders 1200 --requests 200 --lines 320 --seed 20261022 --output data/custom
```

Custom generation requires all three counts. Generated data are deterministic for the same code version, scale, and seed. The reproducibility command generates two temporary datasets and compares every exported-file SHA-256 checksum.

## Outputs

Each output folder contains:

- `returns.sqlite3`: relational database with foreign keys, checks, indexes, and a uniqueness rule preventing duplicate paid refunds.
- One CSV for each relational table, including an append-only `return_events.csv`.
- `ground_truth.csv` and `ground_truth.json`: separate labels for the five deliberately injected cases. These labels are not joined into transaction feature tables.
- `schema.sql` and `seed.sql`: schema and SQLite SQL dump.
- `manifest.json`: row counts, seed, generator version, and SHA-256 checksums.
- `source_manifest.json`: provenance; confirms that all data are synthetic and no external source was used.
- `validation_summary.json`: automated integrity checks and measurable workflow metrics.

Money is stored as integer cents to avoid floating-point rounding. Dates are ISO-8601 calendar dates. Identifiers are deterministic and zero-padded, e.g. `ORD-2026-000001`, `RMA-2026-000001`, `RMAL-RMA-2026-000001-01`, `RTS-2026-000001`, and `REF-2026-000001`.

## Rules and workflow

- Category return windows are 45 days for apparel and 30 days for electronics and home goods. `final_sale` is excluded even with an override. A manager override permits otherwise-late non-excluded returns.
- Requests are created only against purchased order lines. Quantity approval is limited to the requested amount and purchased amount; ineligible lines receive zero approved units.
- Authorizations are `approved`, `partial`, or `rejected`. Authorized returns may have a missing shipment; only received shipments proceed to inspection.
- Inspection conditions map to one inventory disposition: sellable → restock, minor damage → refurbish, missing parts → quarantine, unsafe → scrap. Inventory movement before inspection is blocked.
- Refunds prorate the paid line amount (including allocated discount and tax) by approved quantity. A fixed 499-cent fee is deducted except for damaged returns; exchanges receive no cash refund. Refunds cannot exceed the paid order-line amount, and only one refund per line may be paid.
- Every deliberate exception is isolated to its named record and described in ground truth. Blocked refund attempts are retained as events/records, not silently discarded.

Detailed field definitions, constraints, relationships, and lifecycle states are in [DATA_DICTIONARY.md](./DATA_DICTIONARY.md). AI use and the redacted prompt-history record are in [AI_DISCLOSURE.md](./AI_DISCLOSURE.md).

## Validation and tests

The validator checks foreign keys, primary-key constraints, allowed values (database checks), order arithmetic and totals, quantity eligibility, authorization state, refund reconciliation, disposition sequencing, duplicate payout prevention, event ordering, and ground-truth references and coverage. Validation succeeds only when all checks pass, including confirmation that the known exceptions are labelled and blocked as expected.

Tests cover policy boundaries, fees and rounding, condition-to-disposition mapping, full starter generation, anomaly labels, validation, and fixed-seed reproducibility.

## Known limitations

This is a deterministic assessment/demo simulator, not a production payment or warehouse integration. It uses one currency and calendar-date precision, a compact synthetic catalog, simplified tax allocation, and one authorization/shipment per request. Exchange requests are represented as non-cash returns; replacement-order fulfillment is outside this model. The fixed fee and category windows are explicit sample policy values and should be configured to match a real merchant before operational use.
